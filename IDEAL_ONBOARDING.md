# SentinelOne Connector — идеальный первый запуск

Источник: `ONBOARDING_FIRST_LAUNCH_STANDARD.md`. Целевой пользователь:
SOC-аналитик или security engineer в организации на SentinelOne Singularity,
впервые открывающий приложение — обычно в момент разбора очереди угроз или
настройки нового окружения защиты.

## 1. Credential type
Console URL (тенант-специфичный поддомен Management Console) + API Token,
сгенерированный в Settings > Users > (пользователь) > Generate API Token —
токен статичный, не требует OAuth2-обмена.

## 2. Идеальный флоу (без ограничений SDK)
1. **Console URL как явное отдельное поле с подсказкой** — у SentinelOne нет
   общего API-хоста, у каждого тенанта свой поддомен, видимый в адресной
   строке браузера после логина; без явной подсказки пользователь легко
   перепутает его с адресом другого сервиса или пропустит протокол.
2. **Проверка подключения реальным вызовом перед сохранением** — лёгкий
   `GET /web/api/v2.1/system/status` или `GET /threats?limit=1` сразу после
   ввода credentials, чтобы поймать неверный токен/URL до сохранения.
3. **После успеха — сразу threat queue snapshot** — количество активных
   угроз (не mitigated), не отвечающих (`infected`) agents, и agents не в
   сети >24ч, чтобы дать wow-moment сразу после подключения.
4. **Явное предупреждение перед network isolate/disconnect agent** —
   изоляция обрывает сетевой доступ хоста почти мгновенно; идеально —
   модальное подтверждение с именем машины перед вызовом.
5. **Явное предупреждение перед mitigate (kill/quarantine/remediate/
   rollback)** — особенно rollback-remediation необратимо откатывает
   файловую систему на момент до заражения; нужно явное текстовое
   предупреждение об этом перед выполнением, а не тихое действие.
6. **Понятные сообщения на 401 vs 403** — 401 значит неверный/протухший
   токен, 403 значит, что у токена/пользователя нет нужной роли (Threat
   Operator/Admin для mitigation-действий) — а не голый HTTP-код.
